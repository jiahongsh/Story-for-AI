面向长篇网络小说创作的个人工作区，当前主项目为悬疑都市异能小说《他们不是人》。仓库同时保存原创小说正文、设定与大纲、写作追踪数据、对标拆文资料、市场扫描结果，以及可复用的网文创作 skills。

> **仓库可见性：私有**
>
> 本仓库包含未公开的原创稿件、创作设定和参考资料。请勿在未获得授权的情况下分享仓库、复制正文或将资料用于公开发布。

## 项目简介

这个项目把小说创作拆成几个可以持续维护的层次：

1. **市场与选题**：通过扫榜资料和选题决策，确定题材、平台和读者情绪预期。
2. **对标与拆文**：把参考作品拆成角色、剧情、节奏、情绪模块和世界观等结构化资料。
3. **核心设定**：维护角色、势力、世界观、力量规则、题材定位和正文提示卡。
4. **大纲规划**：先建立全书结构和卷纲，再为每一章建立独立细纲。
5. **正文生产**：按章写入 `正文/`，每章写完后进行一致性、节奏和“去 AI 味”检查。
6. **状态追踪**：使用追踪文件记录角色状态、伏笔、时间线和续写上下文，避免长篇连载过程中出现断档或设定漂移。

项目的核心原则是：**先定情绪，再定故事；先有细纲，再写正文；写完正文，立即更新追踪并自检。**

- **重要意象**：五重老银怀表、定音錾与截时尺、东巷修表铺座钟、黑表鬼市、十二整点终局倒计时。

## 写作文件约定

### `正文/`

长篇正文按章节拆分，每章一个 Markdown 文件，命名格式为：

```text
第001章_章名.md
第002章_章名.md
```

章节编号应连续，章名应能概括本章的主要事件或情绪落点。正文写完后直接保存到 `正文/`，不要只留在聊天记录中。

### `大纲/`

- `大纲.md`：全书总体结构、阶段推进和长期目标。
- `卷纲_第X卷.md`：单卷剧情单元、情绪弧线、人物弧线、伏笔与反转。
- `细纲_第XXX章.md`：单章事件、章节定位、钩子、悬念、爽点和情绪目标。

**写正文前先确认对应细纲存在。** 如果要改变既有剧情方向，先修改或补充大纲，再写正文，避免正文与规划脱节。

### `设定/`

设定按主题拆分，便于按需读取：

- `世界观/`：时代背景、地理、社会规则、能力或力量体系。
- `角色/`：每个重要角色单独一份文件。
- `势力/`：组织、家族、机构、阵营等单独维护。
- `关系.md`：角色关系和关系变化。
- `题材定位.md`：题材核心、读者契约、对标方向和长期升级空间。
- `题材正文提示卡.md`：正文写作时需要持续遵守的边界、期待、节奏和禁漂移规则。

### `追踪/`

追踪目录保存“已经发生的故事事实”和后续续写所需的状态，不等同于大纲：

- `_tracking-state.json`：结构化权威状态。
- `上下文.md`：续写状态卡，快速恢复当前进度。
- `逐章记录/`：每章对后续连续性有影响的紧凑记录。
- `角色状态/`：主要角色当前状态快照。
- `伏笔.md`：当前伏笔视图。
- `时间线/`：作者真相和读者已知信息的时间线。

派生追踪文件应通过项目提供的追踪工具更新，不要随意手工修改后造成多个版本的状态互相冲突。

### `对标/` 与 `拆文库/`

- `拆文库/` 是参考作品的原始拆文数据源。
- `他们不是人/对标/` 是当前创作项目实际引用的对标视图。

写作时优先使用项目内 `对标/` 的结构化资料；需要新增对标作品时，先在 `拆文库/` 完成拆解，再同步与本项目有关的角色、剧情、节奏、情绪模块和设定资料到 `对标/`。

## 推荐工作流

### 1. 初始化或检查环境

```text
/story-setup
```

如果只是检查现有项目，不要在未确认目标的情况下直接开始写正文。先查看当前项目是否存在 `设定/`、`大纲/`、`正文/` 和 `追踪/`。

### 2. 新建项目或导入已有小说

- 新书：先确认题材、平台、核心情绪和读者契约。
- 已有小说：使用 `/story-import` 建立章节、设定和追踪结构。
- 参考作品：使用 `/story-long-analyze` 产出结构化拆文，再把需要的模块同步到项目的 `对标/`。

### 3. 先大纲，后正文

推荐顺序：

```text
选题决策 → 核心设定 → 全书大纲 → 卷纲 → 逐章细纲 → 正文
```

开书或补纲时，默认停在细纲交付，不要因为已有题材设定就自动批量写正文。

### 4. 单章写作

明确指定章节或批次，例如：

```text
写第1章
写第101章
日更2章
续写下一章
修改第10章
```

单轮正文默认控制在少量章节内；如果需要大批量写作，拆成多个批次，以便每批完成检查和追踪。

### 5. 写后检查

每章完成后建议按以下顺序处理：

1. 检查章节是否符合对应细纲。
2. 检查角色状态、时间线、空间位置和道具连续性。
3. 运行 `story-review` 做结构与一致性审查。
4. 运行 `story-deslop` 检查 AI 腔、套话和机械化表达。
5. 更新 `追踪/`，再开始下一章。

### 6. 续写恢复

新会话或长时间中断后，先读取：

```text
他们不是人/追踪/上下文.md
```

涉及具体角色、伏笔或历史事件时，再按需读取对应状态文件、逐章记录和正文，不要无选择地把全部资料塞入一次提示。

## 正文写作规范

1. **每章一个文件**，正文直接写入 `他们不是人/正文/`。
2. **先检查细纲**，缺少对应细纲时先补纲，不要凭空扩写。
3. **每章明确情绪目标**，场景、冲突、信息和结尾钩子都应服务于本章目标。
4. **保持读者契约**，不能为了反转而无视已建立的规则、主角代理权或人物选择。
5. **角色行为要有动机**，重要人物的变化应能在设定、正文或追踪记录中找到依据。
6. **控制信息投放**，区分作者真相与读者已知信息，避免过早泄底或无依据藏信息。
7. **写完立即自检**，不要把连续性检查和去 AI 味检查拖到很多章之后。
8. **保留修改痕迹**，大修前可以建立 Git 提交或分支，便于回退和比较。

## 追踪系统

长篇项目最容易出问题的不是单章文笔，而是跨章节连续性。追踪系统用于记录：

- 当前写到哪一章；
- 角色知道什么、失去什么、正在做什么；
- 伏笔的状态、来源和计划回收位置；
- 作者真相与读者已知信息的差异；
- 下一章写作所需的最小上下文。

建议遵守以下原则：

- `_tracking-state.json` 是结构化状态的唯一权威。
- `上下文.md`、角色快照、伏笔视图和时间线属于派生视图。
- 不要同时维护多份互相独立的“当前进度”。
- 发现追踪状态损坏时先修复追踪，再继续写正文。
- 章节正文是故事事实的主要证据，大纲是计划，不应覆盖已经写成的事实。

## 参考资料与版权边界

仓库中包含参考小说正文、原文资料和拆解文件，主要用于本项目的个人研究、结构分析、节奏学习和对标创作。它们与《他们不是人》的原创正文应明确区分：

- 原创内容主要位于 `他们不是人/`。
- 参考作品原文和拆解资料主要位于 `拆文库/`，部分相关结构化资料位于 `他们不是人/对标/`。
- 参考资料不代表本项目拥有相关作品的版权。
- 使用者应自行确认保存、处理、分析和传播这些资料的合法授权范围。
- 不要将参考原文直接改写成自己的正文，也不要把参考作品中的具体人物、独特情节或表达当作原创成果公开发布。
- 如果未来需要把仓库分享给协作者，建议先清理不必要的参考原文，只保留经授权或可公开使用的分析资料。

由于仓库为私有仓库，仍应避免在 Issue、Pull Request、日志、截图或外部服务中粘贴大段正文与参考原文。

## 隐私、备份与安全

- GitHub 仓库虽然是私有的，但拥有仓库访问权的人仍可能读取全部正文和设定。
- 不要在正文、设定或脚本中保存真实密码、访问令牌、身份证号、住址等敏感信息。
- 涉及真实人物时，建议使用虚构姓名和经过处理的细节。
- 重要版本至少保留 Git 远程仓库和一个独立本地备份，不要只依赖单一设备。
- 删除远程文件前先确认是否仍需要从历史提交恢复；Git 历史中的旧版本不会因为删除当前文件而自动消失。
- 需要公开展示时，优先新建一个经过脱敏和筛选的公开仓库，不要直接把本私有创作仓库改为公开。

## 后续维护建议

1. 每完成一批章节，补齐对应的追踪状态和伏笔视图。
2. 每完成一卷，更新卷纲、人物弧线、时间线和读者已知信息。
3. 定期清理不再需要的临时资料，避免仓库体积持续增长。
4. 参考资料只保留对当前创作仍有用的部分，并记录来源和用途。
5. 大改剧情前先建立 Git 提交，必要时使用分支保存实验版本。
6. 如果更换运行环境，先运行 `/story-setup`，再新开会话加载项目状态。
